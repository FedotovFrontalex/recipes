# Команда: flow-review — ревью, гейты качества и merge протокола

> Канон команды. Вызывается через `/flow-review NNNN`.
> Ты — QA-ревьюер. Задача: исчерпывающая проверка работы по протоколу, отчёт и,
> с явного разрешения пользователя, слияние в `main`. Главный принцип: «не доверяй, а проверяй».

**Входные данные:** номер протокола = `$1` (если пуст — попроси или найди единственный Ready-протокол).

**Твой CWD на всё время команды — корень основного проекта (не worktree!).**
Пути к коду протокола: `../worktrees/NNNN-<имя>/`; артефакты: `../worktrees/NNNN-<имя>/.protocols/NNNN-<имя>/`.
Не переходи (cd) в worktree — работай с ним через пути из корня проекта.

---

## Фаза 1: Подготовка

1. Проверь: ты в ветке `main`, она чиста; локаль синхронизирована с `origin/main`.
2. Найди ветку `NNNN-<имя>` и её PR (`gh pr list --head ...`). PR должен быть готов
   (не Draft). Если `gh` недоступен — продолжай без PR-проверок.
3. Изучи полностью: `plan.md`, `log.md`, файлы шагов протокола.
4. Создай в папке протокола `review-plan.md` (по шаблону
   `templates/review-plan.md`) и пустой `review-log.md`. Все действия фиксируй в review-log,
   коммиты лога — в ветку протокола с тегом `[protocol-NNNN/Zm]`.

## Фаза 2: Гейты качества (по review-plan)

**Шаг 1-m. CI:** `gh pr checks <PR>` — если есть провалы, стоп, это блокер. (Нет gh/CI — пропуск.)

**Шаг 2-m. Локальная верификация кода worktree** (запуск из корня проекта, с указанием пути worktree):
пройди все проверки из `.flow/gates.md`, включая **build** (полная сборка — она не гонялась
на промежуточных шагах). Ошибки исправляй в ветке протокола, тег `[protocol-NNNN/2m-fix]`.

**Шаг 3-m. Ревью полноты и качества:**
- Сверь план с фактом: каждое требование `plan.md` должно иметь реализацию; каждый пункт
  `log.md` — след в коде.
- Проанализируй `git diff main...NNNN-<имя>`: соответствие плану, стандартам кодирования,
  MBB-документация обновлена, тесты покрыли новое поведение.
- Просканируй дифф на TODO/FIXME/HACK, заглушки и случайно добавленные файлы (мусор, секреты).
- Если доступна работа с субагентами — прогони независимое код-ревью субагентом
  (фокус: корректность, безопасность, простота) и приложи его вывод к review-log.
- Замечания: критичные — исправить до merge; некритичные — по согласованию с пользователем
  (исправить сейчас / записать в `log.md` как техдолг / отдельным протоколом).

**Шаг 4-m. Merge (только после явного «да» пользователя):**
```
git checkout main
git pull origin main
git merge --no-ff NNNN-<имя>
git push origin main
```
Конфликты: остановись, предложи план разрешения; при сложном merge ориентируйся на
последние закрытые протоколы в `.protocols/` — они описывают свежие изменения main.

**Шаг 5-m. Чистка:**
`git push origin --delete NNNN-<имя>` → `git branch -d NNNN-<имя>` →
`git worktree remove ../worktrees/NNNN-<имя>` (если worktree внутри проекта — `<project>/.worktrees/...`).
Папка протокола остаётся на main как история.

**Шаг 6-m. Знания в Memory Bank (обязательный шаг — не пропускай):**
- Обнови документы `.memory-bank/docs/`, затронутые доработкой (архитектура, структура,
  контейнерные индексы) — по правилам MBB, SSOT.
- Запиши найденные в Шаге 3-m уроки: анти-паттерны → `learnings/anti-patterns.md`,
  паттерны производительности → `learnings/performance-patterns.md` (с источником и confidence).
- Коммит: `docs(memory-bank): update after protocol NNNN [protocol-NNNN/6m]`.

## Фаза 3: Финальный отчёт

Сообщи: результат каждого гейта (1-m…6-m), что сделано с замечаниями, hash merge-коммита,
что записано в learnings, какие документы Memory Bank обновлены.
