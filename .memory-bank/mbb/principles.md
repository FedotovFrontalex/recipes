# Принципы организации Memory Bank

## 1. Single Source of Truth (SSOT)

**Каждая концепция документирована в единственном месте.**

✅ Правильно: `docs/orchestrator/state-management/state.md` — единственный источник информации о StateManager.
❌ Неправильно: `docs/state-management.md` + `docs/orchestrator.md` — информация о StateManager в двух местах.

Преимущества: нет противоречий, проще поддерживать актуальность, агент находит информацию за один переход.

## 2. Атомарность концепций

**Один файл = одна концепция.** Tier-система размеров:

- Tier 1: ≤ 250 строк — остаётся цельным.
- Tier 2: 250–800 строк — саммари + 1–2 файла детализации.
- Tier 3: > 800 строк — обязательная декомпозиция.

## 3. C4-структура

Организация документации повторяет C4: System → Container → Component.

- **L1 (система):** `docs/product.md`, `docs/architecture.md`, `docs/structure.md` — корень `docs/`.
- **L2 (контейнеры):** `docs/<container>/` — каталоги с собственным контрактом и границами (`api/`, `worker/`, `dashboard/`...). Логические группировки, не являющиеся контейнерами, именуются в скобках: `(packages)/`.
- **L3 (компоненты):** `docs/<container>/<component>/` — детали конкретного компонента.

Каждый контейнер и компонент содержит `index.md` (навигация) и при необходимости `contract.md`, `architecture.md`.

## 4. Duo-файлы (саммари + детали)

Для сложных концепций:

```
component/
├── component.md              # саммари: 150–250 строк, тезисы + аннотированные ссылки
├── component-architecture.md # архитектурные детали
├── component-implementation.md
└── component-examples.md
```

Саммари не повторяет детали, а ссылается на них. Детальный файл может сам стать саммари для под-концепции — вложенность бесконечна, но предсказуема.

## 5. Иерархия информации (градуальное раскрытие)

- Уровень 1: Product overview, architecture diagram, глоссарий.
- Уровень 2: контракты подсистем, API, типовые паттерны.
- Уровень 3: внутренности компонентов, детали реализации.
- Уровень 4: troubleshooting, мониторинг, операционные процедуры.

## 6. Качество текста

- Активный залог: «StateManager обновляет статус задачи», а не «статус обновляется».
- Конкретика: «Redis lock истекает через 30 секунд», а не «lock истекает по таймауту».
- Каждая абстрактная концепция — с примером. Списки предпочтительнее сплошного текста.

## 7. Актуальность

- Версия в frontmatter у каждого файла.
- История изменений (3–5 последних) в `history`.
- Статус: ACTIVE / DRAFT / DEPRECATED. Устаревшее — в `archive/`.

## Антипаттерны (запрещено)

- ❌ Монолитные файлы > 1000 строк без декомпозиции.
- ❌ Дублирование одной концепции в нескольких местах.
- ❌ Сироты: документы без ссылок из индексов.
- ❌ Битые ссылки, неконсистентный frontmatter.

## Чек-лист при создании документа

1. Уровень C4? 2. Место (какой контейнер/компонент)? 3. Не дублирует ли существующее? 4. Нужна ли декомпозиция? 5. Добавлен в ближайший index.md?
